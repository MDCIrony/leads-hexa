Especificación Técnica: Plataforma de Scoring, Enrutamiento y Gestión de Leads
1. Visión General del Sistema
1.1 Objetivo del Proyecto
Construir una plataforma multi-tenant ligera de calificación (scoring) y enrutamiento (routing) de prospectos comercializables (leads). El sistema permite a los usuarios:
* Definir reglas dinámicas de puntuación y asignación de leads.
* Ingestar leads de forma individual mediante Webhooks de Entrada o masiva mediante carga de archivos CSV/XLSX.
* Despachar eventos automatizados (lead asignado, calificado o fallido) mediante Webhooks de Salida.
* Gestionar la asignación de leads a agentes de ventas según políticas configurables (round-robin, mayor capacidad, especialización).
1.2 Principios Arquitectónicos
* Arquitectura Hexagonal (Ports & Adapters): Desacoplamiento total del núcleo de negocio respecto a frameworks de infraestructura (FastAPI, SQLAlchemy, Pandas, httpx).
* Regla de Dependencias Estricta: Las capas internas jamás importan código de las capas externas.
* Testabilidad Offline: El 100% de la lógica de negocio y casos de uso debe poder probarse usando adaptadores In-Memory sin base de datos ni red.
2. Modelo de Dominio y Motor de Reglas
2.1 Entidades y Objetos de Valor (Value Objects)
Lead (Entidad de Dominio)
* id: UUID
* tenant_id: UUID
* first_name: String
* last_name: String
* email: EmailAddress (Value Object)
* phone: String (opcional)
* company: String
* budget: Decimal
* industry: String
* custom_attributes: Dict[str, Any]
* score: int (calculado, valor inicial 0)
* status: Enum (NEW, QUALIFIED, DISQUALIFIED, ASSIGNED, FAILED)
* assigned_agent_id: UUID (opcional)
* created_at: Datetime
ScoringRule (Entidad / Value Object)
Define un criterio numérico que suma o resta puntos al lead.
* id: UUID
* name: String
* field: String (ej: "budget", "industry", "custom_attributes.company_size")
* operator: Enum (EQUALS, NOT_EQUALS, GREATER_THAN, LESS_THAN, CONTAINS, IN)
* value: Any
* score_delta: int (ej: +25, -10)
RoutingRule (Entidad)
Define a quién o cómo se asigna un lead según su puntaje o atributos.
* id: UUID
* min_score: int
* target_team: String
* assignment_strategy: Enum (ROUND_ROBIN, LOWEST_LOAD, DIRECT_AGENT)
* target_agent_ids: List[UUID]
Agent (Entidad)
* id: UUID
* name: String
* email: String
* team: String
* active_leads_count: int
* is_active: bool
WebhookConfig (Entidad)
* id: UUID
* tenant_id: UUID
* event_type: Enum (LEAD_INGESTED, LEAD_QUALIFIED, LEAD_ASSIGNED, PROCESSING_ERROR)
* target_url: String
* secret_token: String (para firma HMAC de seguridad)
2.2 Especificación del Motor de Evaluación de Reglas (Rule Engine)
El motor evalúa una lista de ScoringRule contra los atributos de un Lead.
Operadores Soportados y Lógica de Comparación
Operador
	Aplicabilidad
	Descripción / Ejemplo
	EQUALS
	Str, Num, Bool
	Coincidencia exacta. industry == 'Technology'
	NOT_EQUALS
	Str, Num
	Desigualdad.
	GREATER_THAN
	Numeric / Decimal
	Compara números. budget > 10000
	LESS_THAN
	Numeric / Decimal
	Compara números. budget < 1000
	CONTAINS
	String, List
	Subcadena o inclusión. email CONTAINS '@gmail.com'
	IN
	String, Num
	El valor está presente en la lista configurada.
	Algoritmo de Evaluación de Lead:
1. Inicialización: Lead.score = 0, Lead.status = NEW.
2. Scoring Loop: Por cada ScoringRule activa del tenant:
   * Extraer el valor del campo objetivo del Lead (soporta dot notation para custom_attributes).
   * Evaluar la condición según el operator y value.
   * Si la condición es verdadera: Lead.score += rule.score_delta.
3. Clasificación:
   * Si Lead.score >= threshold_qualified: Lead.status = QUALIFIED.
   * Si Lead.score < threshold_disqualified: Lead.status = DISQUALIFIED.
4. Routing Loop:
   * Si Lead.status == QUALIFIED, buscar la RoutingRule que coincida con la puntuación.
   * Seleccionar agente según assignment_strategy (ej. seleccionar el agente activo con menor active_leads_count).
   * Si la asignación es exitosa: Lead.assigned_agent_id = agent.id, Lead.status = ASSIGNED.
5. Emisión de Eventos: Retornar LeadProcessedEvent con el detalle de ejecución.

3.2 Definición de Puertos Clave (Interfaces Python / abc.ABC)
Puerto de Salida: Repositorio de Leads (LeadRepositoryPort)
from abc import ABC, abstractmethod
from typing import Optional, List
from uuid import UUID
from domain.entities.lead import Lead

class LeadRepositoryPort(ABC):
   @abstractmethod
   def save(self, lead: Lead) -> Lead:
       pass

   @abstractmethod
   def get_by_id(self, lead_id: UUID) -> Optional[Lead]:
       pass

   @abstractmethod
   def list_by_tenant(self, tenant_id: UUID, limit: int = 100, offset: int = 0) -> List[Lead]:
       pass

Puerto de Salida: Despachador de Webhooks (WebhookDispatcherPort)
from abc import ABC, abstractmethod
from typing import Dict, Any

class WebhookDispatcherPort(ABC):
   @abstractmethod
   def dispatch(self, target_url: str, secret_token: str, payload: Dict[str, Any]) -> bool:
       """Envia un payload firmado vía HTTP POST al webhook externo del usuario."""
       pass

Puerto de Entrada: Caso de Uso Ingestar Lead (IngestLeadInputPort)
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import Dict, Any, Optional
from uuid import UUID

@dataclass(frozen=True)
class IngestLeadCommand:
   tenant_id: UUID
   first_name: str
   last_name: str
   email: str
   company: str
   budget: float
   industry: str
   custom_attributes: Dict[str, Any]

class IngestLeadInputPort(ABC):
   @abstractmethod
   def execute(self, command: IngestLeadCommand) -> Dict[str, Any]:
       pass

5. Especificación del Frontend (UI Fullstack MVP)
El frontend será una Single Page Application (SPA) ligera desarrollada en React (TailwindCSS) o Next.js.
Vistas Principales
1. Dashboard de Leads:
   * Tabla con listado de leads ingestados, filtro por estado (NEW, QUALIFIED, DISQUALIFIED, ASSIGNED, FAILED), buscador por correo/empresa y visualizador del score individual.
   * Drawer o Modal para ver el desglose detallado de reglas aplicadas a un lead particular.
2. Constructor de Reglas (Rule Engine Configurator):
   * Formulario interactivo tipo "If [Field] [Operator] [Value] Then Add [Score Delta]".
   * Permite reordenar, activar/desactivar y probar reglas con datos simulados.
3. Asistente de Carga Masiva (Bulk Upload Wizard):
   * Componente Drag-and-Drop para subir archivos .csv o .xlsx.
   * Pre-visualización de las primeras 5 filas del archivo y mapeo dinámico de columnas del archivo hacia los campos esperados por el sistema (email, company, budget, etc.).
4. Configuración de Hooks y Agentes:
   * Gestión de Agentes de Ventas y su estado (Activo/Inactivo).
   * Formulario de configuración de Webhooks salientes con botón para "Send Test Payload".
6. Hoja de Ruta de Implementación para Agentes / Desarrolladores
Para llevar a cabo el desarrollo mediante agentes de código en etapas coordinadas:
Paso 1: Núcleo de Dominio (Domain First)
1. Crear entidades Lead, ScoringRule, RoutingRule y Agent sin ninguna dependencia externa.
2. Crear la clase ScoringEngine con soporte para evaluación de operadores (EQUALS, GREATER_THAN, CONTAINS, etc.).
3. Crear tests unitarios con pytest que prueben múltiples combinaciones de reglas y cálculo de scores.
Paso 2: Puertos y Casos de Uso (Application Layer)
1. Definir los Interfaces (ABCs) en application/ports.
2. Implementar IngestLeadUseCase que coordine: ScoringEngine    Repositorio    Asignación de Agente    Despacho de Webhook.
3. Crear un adaptador InMemoryLeadRepository y InMemoryWebhookDispatcher para probar el caso de uso sin infraestructura real.
Paso 3: Adaptadores de Infraestructura (Backend Driven Adapters)
   1. Crear el adaptador de persistencia con SQLAlchemy (SQLite para dev/demostración rápida, PostgreSQL compatible).
   2. Crear el adaptador PandasFileParser para procesar archivos CSV y Excel.
   3. Crear el adaptador HTTP con httpx para el envío real de Webhooks.
Paso 4: Adaptadores de Entrada (Backend Driving Adapters)
   1. Crear la API REST con FastAPI.
   2. Mapear DTOs de FastAPI (Pydantic models) hacia los Commands del caso de uso.
   3. Configurar el contenedor de inyección de dependencias (dependency_injector o inyección explícita en main.py).
Paso 5: Frontend MVP e Integración End-to-End
   1. Implementar la interfaz gráfica consumiendo la API de FastAPI.
   2. Probar la subida de un CSV con 100 leads y verificar la actualización automática de métricas en el Dashboard.
